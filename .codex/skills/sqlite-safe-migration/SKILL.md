# Безопасная миграция SQLite

## Назначение

Миграция считается успешной только при сохранённой резервной копии, проверенной целостности, сверенных количествах строк и одной голове Alembic. Рабочую БД нельзя использовать для пробного прогона.

## Ранбук

1. Определи точный путь БД и убедись, что он не входит в Git. Прочитай текущую ревизию и список heads.
2. Останови операции, которые могут писать в БД. Скопируй файл БД в отдельную папку вне репозитория с меткой времени.
3. До миграции выполни `PRAGMA integrity_check;`, посчитай строки затрагиваемых таблиц и рассчитай SHA-256 исходной БД и копии.
4. Сначала прогони миграцию на копии или тестовой БД. Для SQLite используй Alembic batch alter (`batch_alter_table`), если операция не поддерживается обычным ALTER TABLE.
5. На тестовой БД выполни upgrade, повторно проверь `integrity_check`, ревизию и количества строк. Объясни каждое изменение количества.
6. После явного разрешения владельца повтори тот же план на рабочей копии, затем проверь, что `alembic heads` возвращает ровно одну голову. При двух головах создай merge-миграцию; не удаляй одну из веток.

## Чек-лист отчёта

- путь резервной копии вне Git;
- SHA-256 до миграции и SHA-256 резервной копии;
- integrity_check до и после;
- ревизия до, целевая ревизия и одна ли голова;
- количества строк до/после по каждой затронутой таблице;
- подтверждение, что рабочая БД не трогалась без команды владельца.

## Типичные ошибки проекта

- запуск `alembic upgrade` по рабочему `ekodez.db` во время диагностики;
- резервная копия рядом с БД или внутри Git;
- использование `btrim()` в SQLite вместо совместимого `trim()`;
- принятие двух heads за успешный результат;
- проверка только ревизии без integrity_check и сверки строк.
