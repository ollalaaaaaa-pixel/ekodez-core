# Ежедневная управленческая сводка в Telegram — дизайн этапа 5

## Цель и границы

Backend ежедневно формирует управленческую сводку за предыдущий календарный день по часовому поясу `Europe/Moscow` и отправляет её владельцу через существующего Telegram-бота. На этапе 5 получателем является только `OWNER_TG_ID`; `ALEXEY_TG_ID` не используется. Этап 6 и полноценная авторизация владельца не входят в работу.

## Состав сводки

Отчётный период — вчера с 00:00:00 включительно до сегодняшних 00:00:00 исключительно по Москве.

- доход и расход: подтверждённые операции (`review_required=false`) с `operation_date` за вчера;
- прибыль: доход минус расход;
- маржа, %: прибыль / доход × 100, при нулевом доходе `0.00`;
- новые заявки: `Lead.created_at` за вчера;
- закрытые заявки: `Lead.closed_at` за вчера; старые строки с `closed_at=NULL` не учитываются;
- спорные операции: операции с `needs_review=true` и `operation_date` за вчера;
- просроченные обработки: актуальные объекты с `next_treatment_date < today` и статусом не `inactive`;
- низкие остатки: актуальные партии, где `quantity < initial_quantity * 0.10`.

Деньги рассчитываются только через `Decimal` и форматируются с двумя знаками. В сообщение не входят телефоны, адреса, имена физических лиц, ИНН и другие PII. Для просроченных объектов допускаются название объекта и дата обработки; для склада — название препарата, остаток и единица. Списки ограничиваются десятью строками с указанием количества остальных элементов, чтобы сообщение оставалось в лимите Telegram.

## Данные и миграция

В `Lead` добавляется nullable `closed_at`. При переходе статуса в `done` поле устанавливается текущим московским временем, если оно ещё пусто. При выходе из `done` поле сбрасывается. Повторная установка `done` не меняет исходное время закрытия.

Создаётся `sent_reports`:

- `id`;
- `report_date` — дата попытки отправки по Москве;
- `report_type` — `auto` или `manual`;
- `recipient_key` — на этапе 5 только `owner`;
- `status` — `sent` или `failed`;
- `sent_at` — время попытки;
- `created_at`.

Каждая попытка создаёт отдельную строку со статусом конкретного получателя. Частичный уникальный индекс запрещает два успешных `auto` за одну дату для одного `recipient_key`, но не мешает сохранять неуспешные попытки и повторять отправку. Manual-кулдаун проверяется только по последней успешной ручной отправке владельцу.

Миграция должна работать на SQLite и сохранять существующие заявки и другие данные.

## Сервис и Telegram

`backend/app/reports/daily.py` содержит независимые операции:

- сбор данных из БД;
- форматирование сообщения;
- отправка одному логическому получателю;
- фиксация результата в `sent_reports`;
- проверка auto-идемпотентности и manual-кулдауна.

Сервис использует существующие `TELEGRAM_BOT_TOKEN` и `OWNER_TG_ID`. Новые переменные окружения и секреты не добавляются. Существующая Telegram-функция получает публичную обёртку для отчётов, не меняя поведение poller.

При отсутствии токена или корректного числового `OWNER_TG_ID` отправка не выполняется, backend продолжает работать, а в структурированный лог попадает warning без значений переменных. При ошибке Telegram создаётся строка `failed`; успешная строка создаётся только после подтверждённой отправки.

## Шедулер

`backend/app/reports/scheduler.py` запускает один daemon-thread при startup FastAPI и вызывает сервис напрямую, без HTTP.

- штатная отправка — 09:00 по Москве;
- контрольные точки догоняющего окна — 10:00, 11:00 и 12:00;
- при старте с 09:00 до 12:59 немедленно проверяется наличие успешного auto за сегодня и при его отсутствии выполняется отправка; последний час даёт допуск на фактическое пробуждение таймера после 12:00;
- после 12:59 auto за текущий день не отправляется;
- перед каждой попыткой проверяется успешная запись `auto/owner` за сегодня;
- исключения перехватываются и безопасно логируются, поток не завершает backend.

Решения о допустимости отправки и следующей контрольной точке оформляются чистыми функциями, чтобы тестировать время без ожидания реальных часов.

## API и health

`POST /api/reports/daily/send`:

- разрешён только при `request.client.host` равном `127.0.0.1` или `::1`;
- `X-Forwarded-For` и другие proxy-заголовки не читаются;
- отправляет отчёт за вчера владельцу;
- возвращает только `status`, `report_date`, `sent_at` и `recipient_key`, без текста отчёта;
- во время 60-секундного кулдауна возвращает HTTP 429;
- без конфигурации Telegram возвращает HTTP 503;
- при подтверждённой ошибке Telegram возвращает HTTP 502.

`GET /health` получает поле `reports`: `ok`, когда токен и числовой `OWNER_TG_ID` доступны и шедулер запущен; иначе `degraded`. Общий `status` остаётся `ok`, чтобы отсутствие Telegram-конфигурации не останавливало приём заявок и остальные функции.

## Проверка и выпуск

TDD покрывает:

- SQLite-миграцию и сохранность старых Lead;
- установку, сохранение и сброс `closed_at`;
- Decimal-агрегацию и формат отчёта без PII;
- внешний запрос с поддельным proxy-заголовком получает 403;
- auto отправляется не более одного раза в день на получателя;
- старт и контрольные точки догоняющего окна 09:00–12:59;
- manual-кулдаун 60 секунд;
- degraded health и безопасный warning без токена/получателя.

Перед миграцией рабочей SQLite создаётся проверенная SHA-256 копия вне Git. После полного gate выполняется реальный localhost POST, цифры сообщения сверяются с dashboard за вчера, владелец подтверждает получение, а скрин сообщения сохраняется вне Git. Итоговый коммит: `feat: daily telegram summary`, затем push в `main` и проверка remote SHA.
