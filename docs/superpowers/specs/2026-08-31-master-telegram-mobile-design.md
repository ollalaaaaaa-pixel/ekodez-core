# Мастер в Telegram и мобильный веб — дизайн

## Цель

Дать Артёму и Алексею короткий выездной сценарий: увидеть активные работы на
сегодня и просроченные, безопасно получить полный адрес и телефон в Telegram,
перенести работу либо закрыть её со списанием препаратов и созданием связанного
дохода. Веб-пульт при этом остаётся локальным и становится пригодным для экрана
шириной 390 px.

## Границы этапа

В этап входят:

- операционные поля заявки и идемпотентная связь заявки с доходом;
- `PATCH /api/leads/{id}` для суммы, даты исполнения, категории, объекта и
  исполнителя;
- Telegram-блок «Работы на сегодня» для allowlist: в автоматической сводке
  09:00 владельцу и по команде `/today`;
- пошаговые действия «Выполнено» и «Перенести»;
- атомарное списание склада, запись обработки и автодоход;
- фильтр «Сегодня», мобильные карточки заявок и склада;
- миграция, резервная копия рабочей SQLite, тесты, живая приёмка и очистка.

Не входят:

- удалённое раскрытие PII через веб;
- новые переменные окружения и новая схема авторизации;
- произвольные Telegram-пользователи и групповые чаты;
- этап 6 мастер-плана;
- реализация этапа «Договоры и акты». После доставки текущего этапа для него
  отдельно уточняется состав и утверждается дизайн.

## Архитектура

Доменная логика выносится в `backend/app/master_workflow.py`. Этот модуль не
зависит от Telegram API: он выбирает активные заявки, переносит дату и в одной
SQLAlchemy-транзакции завершает заявку, создаёт обработку, списывает склад и
при необходимости создаёт доход. `tg_poller.py` отвечает только за allowlist,
кнопки и переходы между шагами.

Состояние незавершённого Telegram-диалога хранится в БД. В нём нет телефона,
адреса, имени, текста сообщения и числового Telegram ID. Ключ пользователя —
логическая роль `owner` или `alexey`, вычисленная из существующих
`OWNER_TG_ID`/`ALEXEY_TG_ID` в момент получения update.

## Модель данных

### Lead

Добавляются поля:

- `amount`: `Numeric(14, 2)`, non-null, Python default `Decimal("0.00")` и
  совместимый с SQLite server default `0.00` для старых строк;
- `execution_date`: `Date`, nullable, индекс; плановая или фактическая дата
  исполнения;
- `performed_by`: `String(50)`, non-null, default «Артём»; допустимы только
  «Артём» и «Алексей».

Существующие `category` и `object_id` используются без бэкфилла и без
автоподбора. `LeadOut.amount` всегда сериализуется строкой с двумя знаками.
При приёме заявки `execution_date` берётся из явного поля ingest, а для старого
Telegram-текста — из даты `order_at`, если она распознана. Сумма берётся из
явного Decimal-поля ingest либо из распознанной строки «Сумма»; отсутствие или
невалидное значение даёт `0.00`, но не роняет приём заявки.

### Transaction

Добавляется nullable `lead_id` с FK на `leads.id` и уникальным индексом
`uq_transactions_lead_id`. SQLite и PostgreSQL допускают несколько `NULL`, но
только одну ненулевую ссылку на конкретную заявку.

Автодоход:

- `source="lead_auto"`;
- `kind="income"`;
- `review_required=false`;
- `currency="RUB"`;
- `amount=lead.amount`;
- `operation_date=lead.execution_date`;
- `category=lead.category` или «Другие работы»;
- `object_id=lead.object_id`;
- `entered_by=lead.performed_by`;
- безопасное описание `Автодоход по заявке #<id>` без PII.

### TelegramMasterDraft

Новая таблица `telegram_master_drafts`:

- `id`;
- уникальный `actor_key`: `owner|alexey`;
- `lead_id` с FK на заявку;
- `action`: `complete|reschedule`;
- `step`: внутренний фиксированный этап диалога;
- `payload`: JSON только с категорией, исполнителем, inventory ID и Decimal-
  количествами в строковом виде;
- `updated_at`: UTC-время на стороне Python.

Начало нового действия заменяет предыдущий черновик этой роли. После успешной
операции или явной отмены черновик удаляется. Перезапуск backend не теряет шаг.

### Миграция

Миграция следует за `e4b7c1d9a205`, использует Alembic batch mode там, где это
нужно SQLite, сохраняет старые строки и проверяется обновлением настоящей
старой схемы до `head`. Перед применением к `backend/ekodez.db` создаётся
timestamped-копия `pre-master-workflow` вне Git. Для исходника и копии
проверяются `PRAGMA integrity_check` и SHA-256; после миграции —
`PRAGMA foreign_key_check`.

## API заявок

### PATCH `/api/leads/{lead_id}`

Частичный payload:

- `amount`: Decimal `>= 0`, не более двух знаков;
- `execution_date`: ISO `YYYY-MM-DD` или `null`;
- `category`: значение общего `INCOME_CATEGORIES_V1` или `null`;
- `object_id`: существующий объект или `null`;
- `performed_by`: «Артём» или «Алексей».

Пустой PATCH возвращает 422. Неизвестная заявка или объект — 404. Неверная
категория, исполнитель, дата или деньги — 422. Endpoint не раскрывает PII и
возвращает обычный замаскированный `LeadOut`.

`RawTextIn` получает необязательные `amount` и `execution_date`, чтобы ручная
форма не делала второй запрос. Старые клиенты продолжают работать.

Старый `POST /api/leads/{id}/status` сохраняется. Переход в `done` через веб
создаёт автодоход по тем же правилам, если сумма больше нуля и задана дата;
при положительной сумме без даты возвращает 422. Материалы через этот старый
endpoint не списываются: полная выездная операция выполняется Telegram-
сценарием.

## Доменный сценарий завершения

Функция завершения получает `lead_id`, категорию, исполнителя, список
`inventory_id + quantity` и признак явного завершения без списания.

Проверки до записи:

1. заявка существует и ещё не выполнена;
2. у заявки назначен существующий объект;
3. категория и исполнитель входят в общие справочники;
4. дата исполнения задана;
5. каждый препарат указан один раз, количество положительно и остатка хватает;
6. пустой список разрешён только после явного выбора «Без списания материалов».

В одной транзакции:

1. создаётся `Treatment` с `lead_id`, объектом, датой, исполнителем и выбранными
   позициями; при явном варианте без материалов история обработки всё равно
   создаётся с пустым списком;
2. остатки уменьшаются условными SQL-update и создаются `ChemicalUsage`;
3. заявка получает категорию, исполнителя, статус `done` и `closed_at` UTC;
4. если `amount > 0` и связанного дохода нет, создаётся автодоход;
5. выполняется один commit.

Недостаточный остаток, ошибка объекта или уникальности откатывают все четыре
действия. Повторное нажатие не создаёт вторую обработку или доход: уже
выполненная заявка возвращает безопасный результат «уже выполнена».

Перенос изменяет только `execution_date`; дата должна быть сегодня или позже.
Статус `new` сохраняется, а `in_work` остаётся `in_work`.

## Telegram-сценарий

### Утренняя сводка 09:00

Автоматическая ежедневная сводка получает секцию «Работы на сегодня» после
существующих финансовых и контрольных показателей. Сейчас автоматическая
сводка отправляется только `OWNER_TG_ID`, поэтому полные адреса и телефоны в
этой секции получает только владелец. Ручная отправка отчёта сохраняет тот же
состав для владельца.

Формирование секции выполняется через общий сервис выборки работ и допускается
только для получателя, который в момент отправки сопоставлен с действующим
allowlist. Когда отдельным этапом будет включён второй получатель Алексей, та
же секция автоматически добавляется его сводке после проверки
`ALEXEY_TG_ID`. Числовые Telegram ID не сохраняются в БД и не попадают в логи.

Если PII недоступны, отдельная заявка показывает маски и отметку о
недоступности полных данных; вся сводка продолжает отправляться. Ошибка одной
заявки не раскрывает шифротекст и не роняет scheduler.

### Доступ и PII

- Обрабатываются только приватные сообщения и callback от ID из существующего
  allowlist `OWNER_TG_ID`/`ALEXEY_TG_ID`.
- Команда `/whoami` остаётся без изменения.
- Команда `/today` и текстовая кнопка «Работы на сегодня» доступны только
  allowlist.
- Никакие proxy-заголовки и веб-доступ не участвуют.
- Для карточки заявки вызывается `decrypt_pii(encrypted_pii)`. Если ключ или
  шифротекст недоступен, бот показывает маски и пояснение, что полные данные
  недоступны; исключение не роняет poller.
- В логах допустимы только событие, `lead_id`, `actor_key` и результат. Адрес,
  телефон, имя, Telegram ID, токен и payload PII не логируются.

### Список работ

Используется московская дата (`Europe/Moscow`). Выбираются заявки со статусом
`new|in_work`, у которых `execution_date == today` или
`execution_date < today`. Заявки без даты, выполненные (`done`) и отменённые
(`cancelled`) не показываются. Сначала идут просроченные, затем сегодняшние.
Одинаковая выборка используется в сводке 09:00, `/today` и веб-фильтре.

Каждая карточка содержит дату, категорию, объект, полные имя/телефон/адрес для
allowlist и кнопки:

- `✅ Выполнено`;
- `📅 Перенести`.

Callback data содержит только короткий код действия и `lead_id` и остаётся в
лимите Telegram 64 байта.

### Выполнение

1. Выбор категории из `INCOME_CATEGORIES_V1` кнопками по две в строке.
2. Выбор исполнителя: Артём или Алексей.
3. Выбор партии препарата с положительным остатком.
4. После выбора препарата бот просит количество с точностью до трёх знаков.
5. После добавления позиции доступны «Добавить препарат», «Завершить» и
   «Без списания материалов». Последняя кнопка доступна только до добавления
   первой позиции.
6. Итоговый экран показывает только рабочие данные без PII: lead ID, категория,
   исполнитель и списания. Кнопки «Подтвердить» и «Отмена».

### Перенос

После «Перенести» доступны «Сегодня», «Завтра», «Через 2 дня», «Через 7 дней»
и «Ввести дату». Для последнего бот принимает `ДД.ММ.ГГГГ`. Прошлая и
невалидная дата отклоняются, черновик сохраняется для повторного ввода. Любой
успешный выбор записывается в `Lead.execution_date`.

Все callback сначала проходят allowlist повторно. Ответы Telegram API имеют
ограниченные повторы; техническая ошибка показывается без внутренних деталей.

## Мобильный веб

### Заявки

- Переключатель «Все / Сегодня»; «Сегодня» использует то же определение, что
  бот: сегодняшние и просроченные `new|in_work`.
- Таблица остаётся на широком экране. При ширине до 767 px отображается список
  карточек, а таблица не рендерится.
- Карточка показывает дату, замаскированные телефон/адрес, услугу, сумму,
  исполнителя, статус и объект.
- Кнопка «Редактировать» открывает форму суммы, даты, категории, исполнителя и
  объекта. Поле в форме заявки подписано нейтрально: «Объект».
- Кнопка «Показать полностью» остаётся прежней и работает только через
  localhost-only endpoint.

### Склад

- На широком экране остаются таблицы.
- При ширине до 767 px остатки и история списаний отображаются карточками.
- Элементы формы занимают ширину контейнера, кнопки имеют touch-target не менее
  44 px, `body` и карточки не создают горизонтальную прокрутку при 390 px.

### Финансовая операция

Существующее действие привязки объекта меняет подпись по состоянию операции:

- если `object_id == null` — «Привязать объект»;
- если объект уже назначен — «Изменить объект».

Обе подписи открывают одну существующую форму выбора объекта и не используют
автоугадывание по контрагенту или описанию.

## Тестирование и приёмка

### Backend TDD

- миграция старой SQLite сохраняет Lead/Transaction и добавляет поля, FK,
  индекс и таблицу черновиков;
- ingest структурирует сумму и дату, сохраняя совместимость;
- PATCH валидирует Decimal, дату, категорию, объект и исполнителя;
- выбор работ учитывает московскую дату, просрочку и финальные статусы;
- автоматическая сводка 09:00 владельцу содержит ту же секцию с полными PII,
  а форматирование для получателя вне allowlist не получает полные данные;
- неallowlist не получает карточки и не может выполнить callback;
- полная PII видна только allowlist, а ошибки расшифровки дают маски;
- перенос валидирует дату;
- завершение с материалами атомарно списывает остаток, создаёт Treatment,
  завершает Lead и создаёт один Transaction;
- недостаточный остаток откатывает всё;
- `amount=0` не создаёт доход;
- повторное подтверждение не создаёт дубли;
- явное «Без списания материалов» создаёт Treatment без ChemicalUsage;
- единый unittest с mock Telegram проходит полный update/callback/text-поток:
  «Работы на сегодня» → «Выполнено» → категория → исполнитель → препарат →
  количество → подтверждение; затем проверяет уменьшение остатка, связь
  `ChemicalUsage -> Treatment.lead_id`, один автодоход с `Transaction.lead_id`
  и отсутствие второго дохода после повторного callback «Выполнено».

### Frontend TDD

- форма редактирования отправляет точный PATCH body;
- фильтр «Сегодня» оставляет сегодня и просроченные активные заявки;
- при мобильном viewport заявки и склад представлены карточками, таблицы не
  используются;
- PII остаётся замаскированной до localhost-подтверждения;
- поле заявки подписано «Объект»;
- финансовая операция показывает «Привязать объект» без связи и «Изменить
  объект» при существующей связи.

### Живая веб-приёмка

1. Зафиксировать исходные `/health`, `/health/db`, показатели дня, dashboard,
   и число тестовых записей.
2. Создать только сущности с уникальной меткой `ТЕСТ MASTER WORKFLOW`.
3. Telegram-сценарий проверить единым E2E-unittest с mock update и реальной
   тестовой БД: карточка «Работы на сегодня» → «Выполнено» → категория →
   исполнитель → препарат → количество → подтверждение; проверить связанное
   списание, один автодоход с `lead_id` и отсутствие дубля после повтора.
4. Через Playwright проверить веб на 390 px и сохранить скриншоты заявок и
   склада вне Git.
5. Удалить только созданные веб-приёмкой IDs в порядке зависимостей.
6. Доказать возврат исходных показателей и отсутствие строк с тестовой меткой.

## Gate и доставка

Перед коммитом выполняются backend `unittest`, `ruff`, `black`, `mypy`,
frontend `test`, `lint`, `build`, `/health`, `/health/db`, HTTP 200 frontend и
проверка отсутствия секретов/БД/скриншотов в staged diff.

Финальный функциональный коммит: `feat: master workflow`, push в `main`, затем
проверка remote SHA. В отчёте: статус, факты, риски, backup без раскрытия пути
с персональными данными, E2E-результаты, очистка и HANDOFF. Этап 6 не начинается
без команды владельца «далее».
