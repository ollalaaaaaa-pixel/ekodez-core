# CORE-BANK-IMPORT-V1-FINAL — импорт XLSX Т-Банка

Статус: `REVIEW`

## Цель и границы

Добавить в Ekodez Core двухэтапный импорт XLSX-выписки Т-Банка: безопасный
предпросмотр и явное подтверждение. Переводы собственных средств и возвраты не
попадают в финансовый результат. Деньги обрабатываются только через `Decimal`,
повторный импорт защищён детерминированным SHA-256.

В версии v1 поддерживается только XLSX Т-Банка с утверждёнными колонками. Другие
банки, OCR, хранение исходного файла, метрика качества правил и история изменения
правил не входят в объём.

## Зависимости и границы модулей

Парсинг выполняется `openpyxl` в режиме `read_only=True, data_only=True`.
Multipart-загрузка FastAPI использует `python-multipart`. В backend создаётся
воспроизводимый список runtime- и quality-зависимостей, поскольку сейчас manifest
зависимостей отсутствует.

`backend/app/bank_import.py` не обращается к БД. Модуль отвечает только за:

- поиск строки заголовков;
- преобразование XLSX-строки в неизменяемый `BankRow`;
- Decimal- и date-нормализацию;
- вычисление `source_hash`;
- детерминированную классификацию в `ClassificationResult`.

`backend/app/main.py` отвечает за HTTP-контракты, проверку активных категорий,
повторное серверное вычисление preview-результата и атомарное сохранение.

## Модель данных и миграция

Следующая миграция после `c4e8a1b7d903` добавляет в `Transaction`:

- `source_hash String(64)`, nullable для старых строк, unique index;
- `doc_number String(50)`, nullable;
- `counterparty_inn String(20)`, nullable;
- `import_batch_id UUID`, nullable;
- `source_filename String(255)`, nullable;
- `needs_review Boolean`, `default=False`, server default `false`.

Nullable у `source_hash` нужен для существующих ручных и Telegram-операций.
Уникальный индекс защищает от конкурентного повторного импорта. Миграция также
добавляет в `expense_categories`, если их ещё нет, категории:

- `Налоги и взносы`;
- `Банковские комиссии`.

`Материалы и химия` также гарантируется при confirm, если справочник старой БД
оказался неполным.

Импортированная подтверждённая запись получает:

- `source="tbank"`;
- `kind="income"` либо `kind="expense"`;
- `needs_review` как аудит первоначальной неуверенности правила;
- `review_required=False`, потому что пользователь уже подтвердил строку;
- общий для запроса `import_batch_id=uuid4()`;
- безопасное имя исходного файла через basename, без пути.

Метрика качества правил в v1 не строится.

## Парсер XLSX

Обязательные колонки:

1. `Тип операции`
2. `Дата проведения`
3. `Номер документа`
4. `Сумма в валюте счёта`
5. `Описание операции`
6. `Назначение платежа`
7. `Наименование контрагента`
8. `ИНН контрагента`

Листы просматриваются по порядку; используется первый лист, в котором найдены все
обязательные заголовки. Строка заголовков ищется в начале листа по
нормализованным точным названиям, поэтому служебные строки банка перед таблицей
допустимы. Пустые строки после заголовка пропускаются. Отсутствующая колонка или
повреждённый XLSX дают HTTP 400 без частичного результата.

Числовая ячейка преобразуется только как `Decimal(str(cell_value))`. Строковая
ячейка очищается от обычных и неразрывных пробелов. Правило разделителей:

- одинарная запятая без точки считается десятичной;
- при наличии запятой и точки последний из разделителей считается десятичным,
  остальные считаются разделителями тысяч;
- результат преобразуется в `Decimal` и `quantize(Decimal("0.01"),
  rounding=ROUND_HALF_UP)`.

Таким образом:

- `1 500 000,50` → `Decimal("1500000.50")`;
- `27,544.00` → `Decimal("27544.00")`.

Дата возвращается как `datetime.date` и сериализуется `YYYY-MM-DD`.

Комментарий операции равен `payment_purpose`; если назначение пустое, используется
`description`.

## Канонический SHA-256

Перед хешированием:

- date: `YYYY-MM-DD`;
- amount: `Decimal`, quantize `0.01`, строка с точкой и ровно двумя знаками;
- doc_number: `strip()`, пустое значение → `""`;
- counterparty_inn: `strip()`, пустое значение → `""`.

Каноническая строка:

```python
hash_string = f"{date}|{amount}|{doc_number}|{counterparty_inn}"
source_hash = hashlib.sha256(hash_string.encode("utf-8")).hexdigest()
```

Confirm не доверяет `source_hash` клиента: повторно нормализует сырые поля,
пересчитывает хеш и отклоняет несовпадение HTTP 422.

## Rules Engine

Сопоставление выполняется case-insensitive по объединённому тексту описания,
назначения и контрагента, но правила, ограниченные назначением или контрагентом,
проверяют именно своё поле. Порядок ниже является частью контракта.

### Кредит

1. Назначение содержит `Перевод собственных средств` либо `Возврат`:
   `is_transfer=True`, строка не сохраняется.
2. `акарицид` или `клещ`: `Обработка от клещей`, channel `Прочее`.
3. `химчистк`: `Химчистка`, channel `Прочее`.
4. `дератизац`: `Дератизация`, channel `Прочее`.
5. `дезинфекц`: `Дезинфекция`, channel `Прочее`.
6. `дезинсекц`, `таракан` или `клоп`: `Дезинсекция`, channel `Прочее`.
7. Непустой ИНН: `Юридические клиенты`, channel `Прочее`,
   `needs_review=True`.
8. Иначе: `Другие работы`, channel `None`, `needs_review=True`.

Юрлицо/ИП определяется только по непустому `counterparty_inn`. Отдельное
эвристическое распознавание по названию в финальный контракт не входит.

### Дебет

1. Назначение содержит `Перевод собственных средств`:
   `is_transfer=True`, строка не сохраняется.
2. Контрагент содержит `МЕДИЛИС` либо описание содержит `Дез средства`:
   `Материалы и химия`.
3. Описание или назначение содержит `ЕНС`, `ФНС` либо `взносы`:
   `Налоги и взносы`.
4. Контрагент содержит `ТБанк` либо описание/назначение содержит `Комиссия`,
   `SMS` или `обслуживание`: `Банковские комиссии`.
5. Иначе: category `None`, `needs_review=True`.

Уверенные правила имеют `needs_review=False`. Сумма всегда хранится положительным
Decimal; направление задаётся `kind`.

## API preview

`POST /api/bank/preview` принимает `multipart/form-data` с одним XLSX-файлом.

Ответ — JSON-массив объектов:

- `operation_type`;
- `date`;
- `amount` строкой с двумя знаками;
- `doc_number`;
- `description`;
- `payment_purpose`;
- `counterparty_name`;
- `counterparty_inn` как сырой неизменяемый атрибут для confirm;
- `counterparty_inn_masked` для отображения;
- `comment`;
- `kind`;
- `category`;
- `channel`;
- `needs_review`;
- `is_transfer`;
- `source_hash`.

Полный ИНН не выводится в логи и не отображается интерфейсом. Frontend хранит
сырой ИНН только для обратной отправки неизменяемых полей confirm.

## API confirm

`POST /api/bank/confirm` принимает:

```json
{
  "source_filename": "statement.xlsx",
  "transactions": [
    {
      "operation_type": "Кредит",
      "date": "2026-08-15",
      "amount": "5000.00",
      "doc_number": "123",
      "description": "...",
      "payment_purpose": "...",
      "counterparty_name": "...",
      "counterparty_inn": "...",
      "source_hash": "...",
      "category_override": "Юридические клиенты",
      "review_confirmed": true
    }
  ]
}
```

Confirm для каждой строки повторно создаёт `BankRow`, хеш и классификацию.
`is_transfer=True` никогда не сохраняется. `category_override` разрешён только
для серверно вычисленной `needs_review=True` строки:

- income override должен входить в `INCOME_CATEGORIES_V1`;
- expense override должен входить в активный `ExpenseCategory`.

Для каждой review-строки обязательны непустой override и
`review_confirmed=True`, иначе весь запрос получает HTTP 422. Override у уверенной
строки также отклоняется, чтобы API не имел скрытого режима ручной переклассификации.

Frontend отправляет в confirm все строки preview, включая скрытые переводы и
возвраты. Это позволяет серверу независимо пересчитать полные обороты выписки.

В одном DB transaction создаётся `batch_id=uuid4()`. Строки с уже существующим
`source_hash` увеличивают `skipped_duplicates`. Уникальный конфликт, возникший
параллельно после предварительной проверки, также считается дубликатом и не
ломает пакет. Ответ содержит количество строк и Decimal-суммы по направлениям:

```json
{
  "imported": 10,
  "skipped_duplicates": 2,
  "batch_id": "...",
  "imported_income_amount": "100000.00",
  "imported_expense_amount": "50000.00",
  "duplicate_income_amount": "0.00",
  "duplicate_expense_amount": "0.00",
  "excluded_credit_amount": "497562.80",
  "excluded_debit_amount": "547562.66",
  "statement_credit_total": "597562.80",
  "statement_debit_total": "597562.66",
  "credit_reconciled": true,
  "debit_reconciled": true
}
```

Инварианты:

- `imported_income + duplicate_income + excluded_credit = statement_credit`;
- `imported_expense + duplicate_expense + excluded_debit = statement_debit`.

На первом импорте duplicate-суммы равны нулю, поэтому импортированные и
отсечённые суммы напрямую сходятся с оборотами банка. Значения
`597 562.80 / 597 562.66` не зашиваются в код и используются только как
контроль ожидаемой реальной выписки.

## Frontend

На странице `Финансы` добавляется кнопка `Импорт выписки (Т-Банк)` и адаптивный
Drawer.

Последовательность:

1. Пользователь выбирает `.xlsx`.
2. Frontend вызывает preview и показывает загрузку либо понятную ошибку.
3. `is_transfer=True` исключаются из таблицы; над таблицей показывается
   `Отсечено переводов самому себе: N`.
4. Таблица показывает дату, направление, контрагента, маскированный ИНН, сумму,
   категорию, канал, комментарий и статус подтверждения.
5. Уверенная категория read-only.
6. `needs_review=True` имеет жёлтый фон, активный Select и кнопку
   `Подтвердить`. Для дохода Select использует `INCOME_CATEGORIES_V1`, для расхода
   — активный справочник `/api/expense-categories`.
7. Кнопка `Подтвердить и сохранить` недоступна, пока каждая review-строка не
   получила допустимый override и явное подтверждение.
8. После confirm показывается notification
   `Импортировано N записей, пропущено M дубликатов` и отчёт сверки: суммы
   импортированных доходов/расходов, суммы отсечённых переводов/возвратов,
   суммы дубликатов, обороты кредита/дебета и статус обоих инвариантов.
9. После закрытия отчёта обновляются операции, итоги и аналитика каналов.

На мобильной ширине Drawer занимает доступную ширину, таблица допускает
горизонтальную прокрутку, основные действия имеют touch-target не меньше 44 px.

## Тестирование и доказательства

Backend unit/integration tests используют только синтетические данные и покрывают:

- `1 500 000,50` и `27,544.00`;
- числовую ячейку через `Decimal(str(cell_value))`;
- Excel date и строковую дату;
- заголовок после служебных строк;
- отсутствующую колонку и повреждённый XLSX;
- все ветки credit/debit в утверждённом порядке;
- маску ИНН;
- комментарий payment purpose с fallback description;
- канонический SHA-256;
- несовпадающий хеш;
- неподтверждённый review;
- недопустимый override;
- transfer/refund, которые не сохраняются;
- повторный confirm: `imported=0`, `skipped_duplicates=N` и отсутствие новых
  DB-строк.
- Decimal-сверку по направлениям, включая синтетический сценарий с оборотами
  кредита `597562.80` и дебета `597562.66`.

Quality gates:

- полный `unittest` backend;
- `ruff check` для backend;
- `black --check` для backend;
- `mypy` для backend с явной конфигурацией;
- frontend `npm run lint`;
- frontend `npm run build`;
- Alembic upgrade до нового head;
- `/health = ok`, frontend HTTP 200, `TG poller: started`.

Приёмка реальной выписки выполняется только на XLSX, который содержит все восемь
обязательных колонок. Найденные в доступных папках XLSX по именам нельзя
однозначно признать банковской выпиской. До обнаружения подходящего файла статус
этой части отчёта остаётся `UNRESOLVED`, а синтетическая приёмка отчётливо
отделяется от реальной.

## Безопасность и Git

- XLSX не сохраняется в репозитории и не коммитится.
- Полный ИНН не попадает в UI-текст, логи, тестовые фикстуры или отчёт.
- Тесты используют синтетические названия и ИНН.
- `.env`, токены, `tg_offset.json`, attachments и `backend/sample_order.txt` не
  индексируются.
- `git add .` не используется.
- Продуктовый коммит:
  `feat: add T-Bank XLSX import with openpyxl, rules engine and SHA-256 idempotency`.
