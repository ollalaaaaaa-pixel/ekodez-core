# CORE-DAY-V1.1 — динамические категории расходов

Статус: `REVIEW`

## Цель

Сохранить простой экран ежедневного ввода, расширить доходы до утверждённого
фиксированного списка и дать владельцу возможность создавать постоянные статьи
расходов без изменения кода. Каждая операция продолжает хранить категорию как
строку, поэтому дневная и последующая месячная аналитика группируют данные по
читаемому названию.

## Доходы

Фиксированный список хранится в `finance_categories.py`:

1. Химчистка
2. Дезинсекция
3. Дератизация
4. Дезинфекция
5. Обработка от клещей
6. Клининг
7. Юридические клиенты
8. Доход от агрегаторов
9. Другие работы

Список используется backend для проверки ручной записи и frontend для строгого
`Select`. Пользователь не создаёт дополнительные категории доходов в версии 1.1.

## Расходы и хранение

Новая таблица `expense_categories`:

- `id` — первичный ключ;
- `name` — `String(100)`, уникальное отображаемое название;
- `is_active` — активность категории, по умолчанию `true`;
- `created_at` — дата и время создания на стороне БД.

Миграция создаёт таблицу и семь исходных записей в заданном порядке:

1. Еда
2. Топливо и машина
3. Материалы и химия
4. Реклама
5. Оборудование и инструмент
6. СИЗ
7. Прочее

Существующие операции не переписываются. Их строковые категории сохраняются.

## API

`GET /api/expense-categories` возвращает активные категории по возрастанию `id`.
Формат элемента: `{id, name}`.

`POST /api/expense-categories` принимает `{name}`. Backend обрезает пробелы по
краям, отклоняет пустое название и название длиннее 100 символов. Дубликаты
проверяются без учёта регистра и лишних крайних пробелов; ответ — HTTP 400.
Защита от одновременного создания обеспечивается уникальным ограничением и
обработкой ошибки целостности.

`POST /api/day/entry`:

- для `income` принимает только одну из девяти фиксированных категорий;
- для `expense` принимает строку категории, но проверяет, что активная категория
  с таким названием существует в справочнике;
- неизвестная или неактивная категория получает HTTP 422 и не создаёт операцию.

`GET /api/day` строит строки расходов по активному справочнику. Если в выбранный
день есть старая операция с категорией, которой уже нет среди активных, она всё
равно остаётся в `entries`, а её сумма добавляется отдельной строкой категорий,
чтобы аналитика не теряла деньги.

## Интерфейс

Общий вид экрана «День» сохраняется: итог дня, две карточки и журнал операций.

В карточке доходов форма добавления использует строгий `Select` из девяти услуг,
поле суммы, комментарий и кнопку сохранения. Под формой остаётся компактная
разбивка сумм по категориям.

В карточке расходов используется `Select`, загруженный через
`GET /api/expense-categories`. Последний пункт — кнопка `＋ Новая категория`.
Она открывает модальное окно с крупным полем названия и кнопкой `Сохранить`.
После успешного POST справочник обновляется, новая категория автоматически
выбирается в незавершённой форме, а пользователь сразу вводит сумму.

Мобильная плавающая кнопка использует те же два `Select` и то же модальное окно.
Интерактивные элементы имеют высоту не меньше 44 px. Ошибки API показываются
понятным уведомлением, введённая сумма и комментарий при ошибке не теряются.

## Тестирование и доказательства

Backend-тесты покрывают:

- точные девять доходных категорий и их классификационные ключевые слова;
- создание и выдачу активных расходных категорий;
- пустое имя, регистронезависимый дубликат и конкурентный дубликат;
- ручную операцию с новой расходной категорией;
- отклонение неизвестной категории;
- дневную агрегацию новой и исторической категории.

Frontend проверяется `lint` и production build. Ручной сценарий создаёт
`Аренда склада`, добавляет расход 5 000 ₽, перезагружает страницу и подтверждает
наличие категории и операции. После доказательства синтетическая операция
удаляется; созданная категория остаётся как требуемая постоянная запись.

Скриншоты: desktop и ширина меньше 768 px с открытым модальным окном создания
категории. Секреты, `.env`, `tg_offset.json`, вложения и `sample_order.txt` в
коммит не входят.
